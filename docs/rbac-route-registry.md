# Konvensi Guard RBAC & Route Registry

> **Berlaku sejak:** PR-019 (Phase 02)
> **Sumber:** SDD §8.2, ADR-001 (batas modul)
> **Kode:** `apps/api/src/core/auth/{rbac,registry}.ts`

## Aturan tunggal

**Setiap route WAJIB menyatakan siapa yang boleh memanggilnya.** Route yang
terpasang di Express tanpa deklarasi akses membuat **boot gagal** — API tidak
menyala sama sekali, bukan menyala dalam keadaan terbuka.

Aturan ini ada karena broken access control hampir tidak pernah lahir dari guard
yang salah, melainkan dari guard yang **lupa dipasang**. Route tanpa penjaga
berjalan sempurna, test-nya hijau (ia memang mengembalikan data), dan tidak ada
satu pun sinyal bahwa sesuatu terlewat. Deklarasi di sini bukan dokumentasi —
ia syarat mount.

## Cara menulis router modul

```ts
import { access, type RouteRegistrar } from "../../../core/auth/index.js";

export function createUsersRouter(controller: UsersController, routes: RouteRegistrar): Router {
  routes.get("/me", access.authenticated(), asyncHandler(controller.me));
  routes.put("/pengguna/:userId", access.self("userId"), asyncHandler(controller.update));
  routes.get("/admin/statistik", access.role("admin"), asyncHandler(controller.stats));
  return routes.router;
}
```

Registrar-nya dibuat di composition root (`boot.ts`), bukan di dalam modul:

```ts
app.use(createUsersModule({ ..., routes: routeRegistry.forModule("/api/v1") }));
```

**Prefix `/api/v1` ada di `forModule()`, bukan di `app.use()`.** Registrar
menuliskan path penuh ke Express DAN ke registry sekaligus, jadi keduanya tidak
mungkin berbeda. Memasang router registry dengan prefix (`app.use("/x", router)`)
ditolak saat boot.

## Lima bentuk deklarasi

| Deklarasi | Penjaga yang dipasang | Pakai untuk |
|---|---|---|
| `access.public(alasan)` | — | Pintu masuk: login, refresh, logout, probe health. `alasan` **wajib** — itulah yang membuat review bisa membedakan "publik karena perlu" dari lupa. |
| `access.internal(alasan)` | token operator (`x-internal-token`) | `/internal/*`: konsumennya operator & monitoring, bukan klien. |
| `access.authenticated()` | `requireAuth` | Resource yang pemiliknya = pemanggil sendiri tanpa param (mis. `GET /me`). |
| `access.role("admin", …)` | `requireAuth` → `requireRole` | Route yang hanya boleh diakses peran tertentu. |
| `access.self("userId", { alsoRoles: ["admin"] })` | `requireAuth` → `requireSelf` | Route ber-param id pengguna. `alsoRoles` adalah SATU-SATUNYA jalan memberi peran lain akses ke resource orang lain — harus ditulis per route. |

Tidak ada nilai "belum diputuskan": deny-by-default berarti penulis route harus
memilih salah satu di atas.

## Perilaku penjaga

| Kondisi | Status | Kode envelope |
|---|---|---|
| Header `Authorization` tidak ada / bukan `Bearer` | 401 | `TIDAK_TERAUTENTIKASI` |
| Token cacat, kedaluwarsa, tanda tangan asing, `ver` usang, akun terhapus | 401 | `SESI_TIDAK_VALID` |
| Peran tidak diizinkan / resource milik orang lain | 403 | `TIDAK_BERHAK` |
| Kunci sesi RS256 belum di-set di server | 503 | `BELUM_SIAP` |

Semua bentuk penolakan token memakai **satu** kode. Membedakan "kedaluwarsa" dari
"tidak dikenal" kepada klien hanya berguna bagi penebak; bagi pengguna jawabannya
sama — masuk lagi.

## Dua hal yang perlu diketahui sebelum menambah endpoint

**1. `requireAuth` membaca DB setiap permintaan.** Klaim `ver` di dalam access
token tidak berarti apa-apa sampai dibandingkan dengan `users.token_version`
terkini — tanpa itu, logout-semua-perangkat (PR-018c) tidak mematikan apa pun
selama 15 menit ke depan. Biayanya satu lookup primary key; akun terhapus juga
langsung kehilangan akses. Cache Redis adalah follow-up, bukan kebutuhan MVP.

**2. Peran diambil dari DB, bukan dari klaim token.** Token membuktikan "siapa";
"boleh apa" dijawab baris user saat ini. Kalau tidak, penurunan hak
(admin → seeker) baru berlaku setelah `ver` di-bump, dan tidak ada yang otomatis
mem-bump saat peran berubah.

## Membaca konteks sesi di controller

```ts
import { authOf } from "../../../core/auth/index.js";

const { userId, role } = authOf(req);
```

`authOf()` **melempar** bila dipanggil pada route yang deklarasinya publik. Itu
disengaja: kondisi tersebut adalah bug pemrograman, dan yang benar adalah 500
yang berisik, bukan 401 yang terlihat wajar.

## Yang ditolak saat boot

`assertRoutesDeclared(app, registry)` di `boot.ts` menolak empat hal:

1. Rute terpasang tanpa deklarasi (bypass registrar lewat `router.get()` langsung).
2. `Router()` polos dipasang di luar registry.
3. Router registry dipasang dengan prefix (path deklarasi jadi berbohong).
4. Deklarasi yang routernya tidak pernah dipasang — kalau dibiarkan, matriks
   authz PR-106 akan menguji endpoint hantu.

## Daftar endpoint untuk audit

`routeRegistry.list()` mengembalikan `{ method, path, access }[]` terurut stabil.
Inilah sumber matriks authz autogenerated (PR-106) dan tempat memeriksa bahwa
tidak ada endpoint yang diam-diam berubah menjadi publik.

## Checklist review PR yang menambah endpoint

- [ ] Route didaftarkan lewat registrar, bukan `router.get()` langsung.
- [ ] Deklarasi akses adalah yang **paling sempit** yang masih membuat fitur jalan.
- [ ] `access.public` disertai alasan yang menjelaskan kenapa sesi tidak mungkin ada.
- [ ] Route ber-param id pengguna memakai `access.self`, bukan `access.authenticated`.
- [ ] `alsoRoles` (bila ada) memang dibutuhkan produk, bukan kenyamanan admin.
